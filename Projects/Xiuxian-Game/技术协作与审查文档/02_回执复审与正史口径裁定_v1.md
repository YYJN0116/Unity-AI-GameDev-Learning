### 对 R1 的重要补充：内容剥离 ≠ 内容保存

**M0 的正确做法是「提取结构、丢弃文本」，不是「把文本原封不动搬进 `data/`」。**

请避免以下两种浪费：

1. **不要为确保「现有内容不丢失」而做细致搬运。** 那些字符串 100% 会被删除，搬运是纯浪费工时。
2. **不要让数据 Schema 长成现有占位内容的形状。** 这是最容易被忽略的风险：如果 `world.json` 的地区/地点字段是照着「后山洞府 / 冷泉谷 / 密林秘境」设计的，或者角色 Schema 是照着「陆青云」的字段设计的，那么等 YY 的新设定交付时，**Schema 本身就要返工**——而 Schema 返工意味着所有已写的校验器、加载器、事件 JSON 一起返工。

**正确姿势**：

- `data/*.json` 按 §6 的 Schema（Event Node / 状态结构 / 数值基线）建立**通用骨架**
- 只放**结构 + 一两个明显是占位的假条目**（例如 `{"id": "placeholder-01", "name": "【占位】", "canon": false}`），用来跑通加载链路
- 真实内容的字段形状，等编剧侧交付第一份样本后再对齐

## 1. 回执复审：六条必须修正的问题

### O1（阻断级）· `data/*.json` + fetch 会摧毁「双击即玩」

回执 §3 R1 计划建立 `data/world.json`、`data/tuning.json` 等并在运行时读取。

**问题**：本项目的核心卖点是零门槛单机运行（交接指南 §1：直接双击 `index.html`）。**浏览器在 `file://` 协议下，`fetch()` 读取本地文件会被 CORS / opaque origin 拒绝。** 现有 `WORLD_DATABASE` 内联在 `app.js` 里，靠 `<script src>` 加载所以没事；一旦改成独立 JSON + fetch，**双击打开将白屏**。

**要求（M0 内决定，不得推迟到 M1）**：

1. `data/*.json` 仅作为**创作源格式**（供编剧侧编写与校验器使用）
2. 新增 `scripts/build-data.js`，把 JSON 打包为 `data-bundle.js`（`window.XIUXIAN_DATA = {...}`）
3. 运行时只加载 bundle，保持双击可用
4. 验收：**双击 `index.html`，8 大行动全部正常**

**请回执明确**：采用 bundle 方案，还是选择放弃 `file://` 支持？（若放弃，必须由 YY 批准——它改变产品定位。）

### O2 · R6 的「字典序确定性消解」与 ambient 权重随机自相矛盾

回执 §3 R6：`main > side > ambient`，同优先级采用字典序确定性消解。

**问题一**：多个 ambient 候选按 id 字典序取第一个 → `ambient.01` 系统性压过 `ambient.02`，**权重形同虚设**，事件分布严重偏斜。

**问题二**：**同一 tick 出现两个满足条件的 `main` 是内容错误，不是待消解的冲突。** 主线互撞必须被拒绝，不能被静默挑一个。

**要求**：

- `ambient` / `side` 候选冲突 → **种子化加权随机**（受 R8 约束）
- 同一 tick 多个 `main` 命中 → **运行时拒绝执行 + 校验器静态报错**（新增校验项）
- 字典序仅保留给「需要绝对确定性且无权重语义」的结构性排序

### O3 · R8 只持久化 seed，读档会重放而不是续接

回执 §3 R8：随机种子固化在 `state.rngSeed`。

**问题**：PRNG 是**有状态序列**。读档时若仅恢复 seed、从序列头开始，玩家读档后继续推进会得到与上次不同的结果——**那是重放，不是续接**。

**要求（任选其一，须写入文档）**：

- `state.rngSeed` + `state.rngCursor`（已消耗次数），或
- 计数器派生：`roll(seed, rollIndex)`，`rollIndex` 持久化

**并新增验收项**：*存档 → 读档 → 继续 → 结果与不存档一次性跑完完全一致。* （回执现有的「存读档后状态复现分毫不差」语义含糊，测不出该缺陷。）

### O4 · R5 的「强制钳制」与 R4 的「Hard Fail」是双标

回执 §3 R4 正确要求「未识别条件操作符必须 Hard Fail」，但 §3 R5 又要求数值「强制区间钳制」。

**问题**：同样是编剧写错，条件错就报错、数值错就静默改。**具体场景**：某选项扣 3 灵石、玩家只有 1 枚 → 静默钳到 0，玩家白拿东西，而且这个错误**永远不会暴露**。

**要求**：

- **消耗类数值必须由 `requires` 前置条件把关**（如 `{"gte": ["currency.lowGradeSpiritStone", 3]}`）
- 执行时若仍会越界 → **报错并中止该 effect**，不静默钳制
- 钳制仅允许用于设计上明确可恢复且必然越界的量（疲劳、修为），且必须在 ledger 中标注「已钳制」

### O5 · Q1 的检定公式缺少属性层，现在无法成立（编剧/数值侧负责，但引擎需等待）

回执 §2.2 采纳 `1d10 + 属性 vs DC`。但当前角色身上可用的数值只有：灵力（单位「缕」，10 起）、修为进度（0–100 百分点）、疲劳（0–100）。**这些都不是检定属性。**

若写成 `灵力 10 + 1d10 vs DC 8`，**几乎恒成功**，判定卡失去意义。

**要求**：

1. 新增**归一化检定属性层**（建议 1–5 小整数评级，由境界、灵根、体质、状态推导），检定只用该层，`1d10 + 评级 vs DC(6–15)`
2. **M0 期间不要将检定公式写入代码。** 等小肥交付 `data/tuning.json` 数值基线（含属性推导规则与 DC 表）后再实现
3. 请回执确认：M0 是否可以不引入任何检定数学

### O6 · F5（炼气九层永久卡死）没有任何工作项

回执 §1 声明认可 F1–F5，但 R1–R11 与 M0–M3 中**没有任何一条对应 F5**。

**事实**：`可运行测试第一版/app.js:916-936` 的突破分支在炼气九层之后只输出一句「需备齐筑基丹」的叙事，**没有任何代码路径能把境界设为「筑基」**。

**要求**：为 F5 建独立工作项，挂在 M3（第一卷内容接入、筑基剧情落地）。至少现在登记，避免遗漏。

## 2. 正史口径裁定（YY，2026-10-16）

### 2.1 裁定内容

> **世界观与基础设定跟随 `xiuxian_working_v1.5/`，以 `01_GM_True_History.md` 为核心锚点。要重写、重新讨论的是游戏的剧情与人物层。**

### 2.2 这条裁定推翻了小肥 v1 报告 §1.3 的框法（主动更正）

v1 报告把三套设定并列为「三套互相矛盾的正史，请 YY 挑一套」。**这个框法是错的。** 逐项核查后的事实是：

| 来源 | 真实性质 |
|---|---|
| `xiuxian_working_v1.5/`（41 份） | **唯一的设定源。** 含底层真相、运行规则、候选地点 |
| 交接指南 §5.1 的示例状态 | **手写示例，不是设定。** 其中的「青冥洲 / 青云坊市」不见于工作集 |
| `app.js` 的 `WORLD_DATABASE` 与 `策划与世界观设计文档/world-database.json` | **原型阶段的占位内容。** 该文件自身即声明 `catalogStatus: "candidate_catalog"`、「条目源自 game-design.md 的建议清单，都是候选，不自动成为本局正史」 |

所以命题不是「挑一套」，而是「**以工作集为准，另外两套作废**」。

### 2.3 工作集里到底有什么（已逐项核对）

**有 = 锁定，不得擅自改动：**

1. **世界底层法则与真相**（`01_GM_True_History.md`）：灵气是会在天地、生命、地脉与更深层空间之间缓慢循环的体系，不是无限燃料；高阶修行本身并非错误，问题出在古代技术强行锁定 / 抽取 / 改道灵气循环；飞升不是渡劫后必然发生的流程，古籍把数种不同结果统称「飞升」；两次重大历史转折（约八百至一千年前 / 近数百年）；历史矛盾的五个来源（局部观察、地区差异、抄写转述误差、势力为正当性删改、少数伪造），**主持端不得一概归因为阴谋**；不存在掌握全部真相的全知幕后黑手；世界**并非**处于末日倒计时。
2. **运行规则与数值口径**（`12 / 13 / 16 / 20 / 26 / 27 / 30` 等）：行动结算、时间换算、物价分层基线；境界成长使用**状态、证据与条件清单**，明确不采用固定天数自动升级或伪精确百分比。
3. **一个候选开局地点**（`17_GM_Opening_Region_Concrete_Draft_v0.1.md`）：**临川镇**，文件内明确标注「**暂定地名**」，含路程、三类本地组织、四个可选事件种子，并声明「不是强制开局」。

**没有 = 这正是你要新写的部分：**

- 大陆 / 州的正式名称（**工作集内不存在「青冥洲」**）
- 宗门的正式名称与势力总表（`09_GM_Event_Web_v0.2.md` 出现「玄衡道盟 / 百川行会 / 书院」，但那是事件素材中的参与者，不是一份正式势力表）
- 主角 —— 工作集走的是 `21_GM_Character_Creation_Protocol`（玩家自建或授权随机生成），**没有预写主角「陆青云」**
- 第一卷的剧情、人物、事件

### 2.4 需要 YY 注意的来源问题

「青云坊市 / 青冥洲」这两个名字的**唯一来源是交接指南的示例文本**：`00_项目全景与技术交接指南.md:109` 的示例角色背景、`:127-129` 的示例世界状态，以及 `:181` 的讨论示例「如《青云坊市篇·散修起步》」。它们是**前一个 AI 阶段手写的举例，不是设定集里的条目**。

这不代表不能用——这是 YY 的世界，当然可以采用。但必须**明确裁定并登记进设定集**，否则会出现「作者以为是正史、设定集里查不到」的悬空设定，后续协作者会各自脑补。

## 3. 对 M0 的修订要求（由 §2 裁定直接推出）

### 3.1 `data/world.json` 不得把占位内容洗成 canon ⚠️ 重要

回执 §3 R1 计划把 `WORLD_DATABASE` 搬进 `data/world.json`。

**若照搬现有内容，等于把前一个 AI 编的占位地名——晨曦大陆 / 后山洞府 / 玄风宗 / 冷泉谷 / 密林秘境 / 禁地前沿——固化成「正式数据文件」**，将来还要再洗一次；更糟的是，后续接手的协作者极可能把它们误认为正史。

**要求**：

1. M0 的 `data/world.json` **只放结构骨架**（`continents` / `regions` / `locations` / `factions` 空数组 + 字段注释），真实地理待编剧侧交付
2. 若为跑通链路必须放占位条目，**每条必须带显式标记**（如 `"canon": false, "placeholder": true`），且校验器对 `canon: false` 的条目在正式内容接入前给出警告
3. R1 验收标准加强为：*引擎代码中不出现任何修仙地名 / 人名 / 势力名，**且 `data/world.json` 中不存在任何未经 YY 裁定的地名被标记为正史***

### 3.2 交接指南与 README 存在事实错误，建议一并修正

- `00_项目全景与技术交接指南.md:36` 称工作集沉淀了「……**青冥洲**势力图谱等」
- `README.md:14` 称工作集包含「**青冥洲**地理、三方宗门」

**经全目录递归检索，`xiuxian_working_v1.5/` 内不存在「青冥洲」，也不存在「青云坊市」；唯一的地点候选是「临川镇」。** 这两处描述会使下一个接手的 AI 照着去编造一个不存在的「青冥洲」——本次交接中已经发生过一次这种误读。

**建议修正为**：「含候选开局地区临川镇、三类本地组织、世界底层历史与运行规则；所有名称均为候选，待正式采用。」
