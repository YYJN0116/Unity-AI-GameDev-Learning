## 0. 重要更正：D2 关系模型与设定集规则冲突，需要修订

### 0.1 冲突事实

《交接报告 v1》提出的 **D2**「好感度不做连续数值，改为离散阶段（陌生 / 相识 / 信赖 / 生死之交）+ 因果记录」，已被 YY 采纳，且 Antigravity 已在《03 报告》§2.1 中宣布「**正式确立** stranger / acquainted / trusted / sworn 四阶状态」。

**但这条与设定集的既有规则直接冲突。** `10_GM_Key_NPC_Motivation_Dossiers_v0.1.md` 第 75 行的「人物运行共通规则」第 3 条原文：

> **关系分开记录：好感、信任、欠债、恐惧、尊重、利益依赖不互相等价。**

我的四阶阶梯把「好感」（acquainted）与「信任」（trusted / sworn）压在了**同一条轴**上——正是这条规则明文禁止的做法。

### 0.2 责任归属

**这是我的错，不是 Antigravity 的。** 我当时只想着「不要连续浮点数」和「不要分支爆炸」，做了一次过度简化，没有回去核对设定集里关于人际关系的既有规则。Antigravity 是照我的规格实现的。

### 0.3 修订方案：多维离散（取代单轴阶梯）

**保留 D2 的原意（不使用连续数值），改为按设定集要求分轴记录。**

```jsonc
{
  "npcId": "npc.<slug>",
  "affinity":  "cold | neutral | warm | close",              // 好感：纯粹的情感倾向
  "trust":     "suspicious | wary | trusting | reliant",     // 信任：是否相信其言行
  "respect":   "dismissive | neutral | respectful | reverent", // 尊重：对其能力/品格的评价
  "fear":      "none | wary | fearful",                      // 恐惧：源于实力差距或把柄
  "obligations": [                                           // 人情/债务：列表，不是标量
    { "direction": "playerOwes | npcOwes", "what": "", "sinceInGameDate": "", "settled": false }
  ],
  "interests": [                                             // 利益依赖：标签列表，不是标量
    { "kind": "", "description": "" }
  ],
  "log": [                                                   // 因果记录（沿用 D2 原有设计）
    { "atInGameDate": "", "cause": "", "changed": "" }
  ]
}
```

**为什么这样对：**

| 要求 | 依据 | 是否满足 |
|---|---|---|
| 不使用连续数值 | D2 原意 | ✅ 全部为枚举档位 |
| 好感与信任分离 | `10` 规则 3 | ✅ 两条独立轴 |
| 债务不折算成通用点数 | `v0.1-data-standard.md:120`「人情、名声、关系、债务……不折算成通用点数」 | ✅ 债务为事件列表 |
| 关系变化必须有原因 | D2「因果记录」 | ✅ `log[].cause` |
| 与 UI 可呈现 | 左栏「道友与人脉」 | ✅ 每轴显示档位文本即可 |

**典型场景验证**：一个 NPC 可以「好感 warm（人品不错）但信任 suspicious（他的情报来源不可靠）且 fear wary（境界高你两阶）」。单轴阶梯**无法表达**这个状态，而它在设定集里是常态——`10` 里六个原型几乎都是这种结构。

### 0.4 对 Antigravity 的影响

- 这是**接口变更**，须走变更流程（改 Schema → 升版本 → 写 changelog）
- 由于 T1 已经要求重写 `state-template.json`，**本次修订可以搭车完成，不额外增加一次返工**
- 影响面：`relationships[]` 结构、`relation.set` 效果操作符、校验器、左栏人脉 UI

## 1. 人物卡的两种类型

| 类型 | 用途 | 依据 |
|---|---|---|
| **NPC 卡** | 每一个有名字、会行动、有认知边界的人物 | `02` §3 档案模板 + `10` 九段结构 |
| **主角卡** | 玩家角色的开局配置 | `21` 角色创建协议 + `v0.1-data-standard.md` §2 + 状态结构 |

两者**不要混用同一张卡**。主角没有「隐藏矛盾 / 保守秘密的动机」这类 GM 侧字段；NPC 没有「灵根 / 修为进度」这类运行时属性。

## 2. NPC 卡字段规范

字段分三组：**A 设定集必填**（来自 `02` §3）、**B 动机结构必填**（来自 `10` 的九段式）、**C 引擎字段**（本规范新增）。

### A 组 · 档案模板（`02_GM_Factions_NPC_Framework.md` §3 原文）

| 字段 | 说明 |
|---|---|
| `npcId` | 稳定 ID，见 §4 命名规范 |
| `姓名` | 显示名 |
| `当前身份` | 在势力/地方中的位置 |
| `大致年龄与境界` | 允许模糊（如「中年，筑基前后」）；不得给出无依据的精确值 |
| `外在表现` | 他人能直接观察到的部分 |
| `私人目标` | 不公开的近期目的 |
| `长期目标` | 跨越章节的意图 |
| `眼前压力` | **驱动他"现在"行动的原因**——这一项最容易被写空，也最关键 |
| `能力与限制` | 他能做什么、不能做什么 |
| `资源与债务` | 可调动的资源、欠人与被欠 |
| `当前地点` / `时间安排` | 他在哪、什么时候在哪 |
| `真实掌握的信息` | 他确实知道的 |
| `错误信念` | 他信以为真但错误的事 |
| `不知道的关键事项` | **必须显式写出他不知道什么** |
| `对玩家的态度` | 当前态度 |
| `信任程度` | 见 §0.3 分轴 |
| `已记录互动` / `关系变化原因` | 因果日志 |
| `已知秘密` | 他掌握的秘密 |
| `保守秘密的动机` | 为什么不说 |
| `愿意透露的条件` | 什么情况下会说 |
| `可能采取的行动` | 他会主动做什么 |
| `行动前置条件` | 什么条件下才会做 |
| `失败或受阻后的替代方案` | **不允许「无替代方案」** |
| `可发现线索` | 玩家能查到什么 |
| `玩家可能误解的表象` | 故意留出的误读空间 |
| `与其他档案的关联` | 交叉引用其他 NPC / 事件 |

### B 组 · 动机九段（`10` 结构，作为 A 组的强制补充）

`核心目标` / `次要需求` / `公开立场` / `隐藏矛盾` / `知道什么` / `不知道什么` / `会做什么` / **`不会无缘无故做什么`** / `可能转变`

> `不会无缘无故做什么` 是这套文档里最有价值的一栏，它把「NPC 变成剧情工具」这件事堵死了。**每张卡必须填。**

### C 组 · 引擎字段（本规范新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `npcId` | string | 稳定 ID，见 §4 |
| `factionId` | string \| null | 必须存在于 `data/world.json` 的 `factions` |
| `currentLocationId` | string | 必须存在于 `world.locations` |
| `status` | enum | `确定 / 暂定 / 传闻 / 已废弃`（沿用 `00_GM_Index` §4 的设定记录格式） |
| `canon` | boolean | 与 `world.json` 同一约定；未定稿时为 `false` |
| `relationAxes` | object | 见 §0.3 |
| `flagsOwned` | string[] | 本 NPC 会设置的 flag，命名 `npc.<slug>.<flag>` |
| `relatedEventIds` | string[] | 相关事件 id，用于校验器反向完整性检查 |
| `knowledgeBoundary` | object | 由 A 组的三个字段机器化：`{ knows: [], believesWrongly: [], unawareOf: [] }` |
| `reactionRules` | array | 结构化「可能转变」：`{ when: <Condition>, then: <Effect[]> }`，见 §6 |

## 3. NPC 卡模板（可直接复制填写）

```markdown
## NPC-<序号>｜<姓名>（<npcId>）

**标签**：status=<确定/暂定/传闻> · canon=<true/false> · 势力=<factionId 或 无> · 当前地点=<locationId>

### 一、他是谁
- 当前身份：
- 大致年龄与境界：
- 外在表现：

### 二、他要什么
- 核心目标：
- 次要需求：
- 私人目标：
- 长期目标：
- **眼前压力**：            ← 驱动他现在行动的原因，禁止留空

### 三、公开与隐藏
- 公开立场：
- 隐藏矛盾：                ← 羞耻 / 私人利益 / 责任 / 有限知识，不得升级成世界阴谋
- 已知秘密：
- 保守秘密的动机：
- 愿意透露的条件：

### 四、能力与处境
- 能力与限制：
- 资源与债务：
- 时间安排：

### 五、认知边界（三栏必填）
- 真实掌握的信息：
- **错误信念**：
- **不知道的关键事项**：

### 六、行动逻辑
- 可能采取的行动：
- 行动前置条件：
- 失败或受阻后的替代方案：   ← 禁止填「无」
- **不会无缘无故做什么**：    ← 禁止留空

### 七、与玩家的关系（分轴记录，不得合并）
- 好感 affinity：cold / neutral / warm / close
- 信任 trust：suspicious / wary / trusting / reliant
- 尊重 respect：dismissive / neutral / respectful / reverent
- 恐惧 fear：none / wary / fearful
- 人情与债务 obligations：
- 利益依赖 interests：
- 关系变化日志 log：

### 八、剧本接口
- 可发现线索：
- 玩家可能误解的表象：
- 与其他档案的关联：
- 相关事件 id：
- 会设置的 flag：
- 可能转变（结构化）：when <条件> → <效果>
```

**填写纪律（摘自设定集，逐条遵守）：**

1. 人物目标可冲突，但必须可解释；**「因为剧情需要」不是动机**（`10` 规则 1）
2. 人物的秘密先是私人利益、羞耻、责任或有限知识，**不自动升级成世界阴谋**（`10` 规则 2）
3. 人物改变立场需要**新证据、代价、经验或利益变化**；不能靠一句漂亮台词瞬间改观（`10` 规则 4）
4. 人物可以误判，但**须记录其误判来自何种信息缺口或偏见**（`10` 规则 5）
5. 人物死亡、离开或失势后，其**承诺、文件、债务与影响仍可能延续**（`10` 规则 6）
6. **NPC 可主动行动，但不得替玩家决定玩家角色的行动或内心**（`02` §4）

## 5. 主角卡规范

**主角卡 ≠ NPC 卡。** 主角卡的字段由运行时状态结构决定，必须逐字段对齐 `v0.1-data-standard.md` §2（也是《04 报告》T1 要求 `state-template.json` 对齐的那份标准）。

必填字段：`id` / `name` / `age` / `background` / `identity` / `spiritualRoot` / `constitution` / `realm` / `cultivationProgress` / `spiritualPower` / `fatigue` / `inventory` / `currencyBalances` / `relationships` / `injuries` / `reputation` / `debts` / `goals` / `activeTasks`

开局模板额外包含：

- `startLocationId`：必须存在于 `world.locations`
- `openingFlags`：开局即置位的 flag
- `resourceBudget`：开局资源预算（对齐 `28_GM_Starter_Balance_Profiles` 的模板口径，具体数值由数值基线定）
- `canon`：未定稿为 `false`

**注意**：主角的「背景 / 身份 / 开局资源」属于**剧本决策**，本规范只定义字段与约束，不预设内容。`21_GM_Character_Creation_Protocol` 规定正式开局需先确认「是否采用候选开局地区」与「自建还是随机生成」，应保留为玩家可选流程。

## 6. 交给 Antigravity 的实现要求

> 按 YY 的分工：**小肥出规范与验收标准，Antigravity 负责实现。** 以下每条都带验收方式。

| # | 要求 | 验收方式 |

| **C2** | 校验器新增 NPC 卡校验：§2 A/B 组必填字段缺失即报错；`眼前压力`、`不知道的关键事项`、`不会无缘无故做什么`、`失败或受阻后的替代方案` 四栏为**硬性必填** | 故意删掉「不会无缘无故做什么」，校验器精准报错定位到 npcId + 字段 |
| **C3** | 引用完整性：`factionId` / `currentLocationId` / `relatedEventIds` 必须在 `world.json` 与事件库中存在，悬空即报错 | 写一个不存在的 locationId，校验器报错 |
| **C4** | flag 命名空间校验：`npc.<slug>.*` 形式的 flag 必须由该 NPC 的 `flagsOwned` 声明，或由事件 effect 显式设置 | 使用未声明的 flag，校验器告警 |
| **C5** | 左栏「道友与人脉」UI 按轴呈现（不合并成单一进度条）；未设定的轴显示「未设定」，**不得静默替换为默认档位** | 视觉核对 |
| **C6** | 人物档案数据的存放位置：建议 `data/npcs/*.json`，命名与 `data/starters/` 一致，由 `build-data.js` 一并打包 | `data-bundle.js` 中包含 npcs 节点 |

**关于人物档案的存放形式**：设定集里的 NPC 档案是给人读的 Markdown（含大量散文式描述），而引擎需要结构化 JSON。建议**双轨**：

- `data/npcs/*.json`：引擎可用的结构化字段（认知边界、关系轴、flag、反应规则）
- 剧本侧 Markdown：完整的九段式叙述（供 YY 与后续协作者阅读）

两者由 `npcId` 关联。**不要在 JSON 里塞长散文，也不要在 Markdown 里塞结构数据**——两边都会变难维护。

## 7. 六类 NPC 原型的处理方式

`10_GM_Key_NPC_Motivation_Dossiers_v0.1.md` 已定义六类关键人物原型（记录校勘者 / 地方阵务守护者 / 商路风险经纪人 / 道盟地方协调员 / 旧知识继承者 / 凡人地方中间人），并规定「**名字、境界、外貌与具体所在地应按开局需要生成**。这里固定的是动机结构和认知边界」。

**本规范不复制这六份档案**，理由：复制就会有两处维护、必然漂移。处理方式：

1. 这六类是**原型（archetype）**，提供的是动机骨架
2. 第一卷的每个具体 NPC = **一个原型 + 一个具体身份 + 一个具体处境**
3. 具体化时，卡上需注明 `archetypeRef: "NPC-03"` 以便回溯

**这带来一个对剧本阶段的硬约束**：第一卷出现的所有 NPC，其动机结构必须能对应到六类原型之一（或明确声明是新原型）。**不允许出现「因为剧情需要所以他要这么做」的人物。**
