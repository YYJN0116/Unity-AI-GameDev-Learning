## 3. 必须修正的问题

### T1（严重）· `state-template.json` 的 Schema 长歪了 —— 退回了被废止的旧示例

这是本轮最重要的问题。`state-template.json` 的 `character` 结构**没有采用 `v0.1-data-standard.md` 与 `app.js` `makeInitialState()` 的既有字段**，而是采用了**《00_项目全景与技术交接指南》§5.1 示例状态**的形状——而那份示例正是《修仙记录簿_引擎改造交接报告 v1》§1.4 判定为**违反 v0.1 标准**的那一份。

逐字段对照：

| 字段 | 交付物中的写法 | 应为（依据） | 问题 |
|---|---|---|---|
| `character.spiritRoots` | `["无属性"]`（数组） | `spiritualRoot: ""`（单数字符串）<br>依据：`v0.1-data-standard.md:49`、`app.js:196` | 字段名与类型均不符 |
| `character.vitality` | `{ "current": 20, "max": 20 }` | **该字段不应存在**<br>依据：`v0.1-data-standard.md:94`「**不将伤势与生命值混用为一个字段**」 | 且与同文件内的 `injuries: []` 形成**双轨记伤势** |
| `character.spiritualPower` | `{ "current": 10, "max": 10 }` | `{ value, unit, controlState }`<br>依据：`v0.1-data-standard.md:57-61` | 丢失 `unit` 与 `controlState` |
| `character.fatigue` | `{ "value": 0, "status": "精力充沛" }` | `{ value, scaleId, description }`<br>依据：`v0.1-data-standard.md:62-66` | 丢失 `scaleId`；`status` 应为 `description` |
| `character.currencyBalances[0]` | `{ "currency": "下品灵石", "unit": "lowGradeSpiritStone", "amount": 0 }` | `{ unit, amount }`<br>依据：`v0.1-data-standard.md:96` | 多出 `currency` 显示名字段，与 `unit`（机器 id）语义冲突 |
| `character.id` | **缺失** | `v0.1-data-standard.md:44`、`app.js:195` | 丢失 |
| `character.age` | **缺失** | `v0.1-data-standard.md:46` | 丢失 |
| `character.identity` | **缺失** | `v0.1-data-standard.md:48` | 丢失 |
| `character.constitution` | **缺失** | `v0.1-data-standard.md:50` | 丢失 |
| `character.reputation` | **缺失** | `v0.1-data-standard.md:71` | 丢失 |

**要求**：

1. `state-template.json` 的 `character` 结构**逐字段对齐 `v0.1-data-standard.md` 第 35–86 行**（可保留 `vitality` 之外的一切新增字段）
2. 若认为 v0.1 标准本身需要修订（例如确实想要 `vitality`），**必须走接口变更流程**：改标准 → 升版本 → 写 changelog → 双方确认。不得在数据文件里单方面引入
3. 补回 `id` / `age` / `identity` / `constitution` / `reputation`

**说明**：这不是"内容对不对"的问题，而是"接口定义漂移"的问题。这正是《02 报告》第 0.1 节警告过的「Schema 长成占位/示例的形状」。**数据骨架的文件名对了，不等于字段对了。**

### T2 · `tuning.json` 三处问题

**T2-a：`lowGradeSpiritStone` 被错误标记为占位**

```json
"lowGradeSpiritStone": {
  "displayName": "下品灵石",
  "unit": "枚",
  "canon": false,        // ← 错
  "placeholder": true    // ← 错
}
```

灵石是 `v0.1-data-standard.md:96` **明确规定**的货币单位（`{ "unit": "lowGradeSpiritStone", "amount": 0 }`），是既成决定，**不是占位内容**。标成占位会导致：校验器对真实存在的货币持续发警告；后续协作者误以为可以随意改名或删除。

**要求**：移除 `canon` / `placeholder` 标记。

**T2-b：漏了 `fragment`（碎灵）**

`v0.1-data-standard.md:115` 规定「**10 枚碎灵 = 1 枚低阶灵石**；换算只用于记账，不代表所有交易都接受兑换」。`tuning.json` 的 `currencies` 只有 `lowGradeSpiritStone`。

**要求**：补 `fragment`，并补上换算率字段（建议 `exchange: { to: "lowGradeSpiritStone", rate: 0.1, ledgerOnly: true }`）。

**T2-c：`unit` 一词两义**

`currencies.lowGradeSpiritStone.unit` 的值是「枚」（计量单位），而 `state.currencyBalances[].unit` 的值是「lowGradeSpiritStone」（货币 id）。**同一个字段名承担两种语义，早晚出事。**

**要求**：`currencies.*.unit` 改名为 `displayUnit`。

### T3 · `build-data.js` 缺少防漂移校验（生成型文件的最大风险）

**问题一：产物不可复现。** `bundleData.buildTime = new Date().toISOString()` 使每次执行都产生不同的文件，**git diff 永远为脏**，无法通过哈希判断产物是否最新。

**问题二（更严重）：没有任何机制验证「已提交的 `data-bundle.js`」与 `data/*.json` 是否同步。**

《03 报告》§1 计划「在 CI 与 `npm test` 中自动串联 `build-data.js`」。但**"串联 build" 不等于"校验同步"**——`build` 会把陈旧产物直接覆盖成新的，反而把"有人改了 JSON 忘了 build"这个问题**掩盖掉**，游戏会静默使用旧数据。这与本项目此前在玩家安全包上遇到的漂移问题同源。

**要求**：

1. 新增 `--check` 模式：在内存中重新构建，与磁盘上的 `data-bundle.js` 比对，不一致则 **`exit 1`** 并打印差异摘要
2. CI 与 `npm test` 中串联的是 `build-data.js --check`，**不是** `build-data.js`
3. 把 `buildTime` 从产物中移除，改为写入**输入内容的哈希**（如 `inputsHash: "sha256:..."`），既消除 diff 噪声，又让 `--check` 可用哈希直接比对

### T4 · `validate-schema.js` 覆盖面不足

当前实际校验的内容：

- `world.json`：`schemaVersion`、三个数组类型、id 唯一、`name` 存在、`canon:false` 警告
- `tuning.json`：`schemaVersion`、`fatigue` 有 min/max、`actions` 是对象
- `starters/*.json`：id 存在且唯一、有 `character` 对象、`canon:false` 警告

**缺失项**：

| 缺失 | 严重性 | 说明 |
|---|---|---|
| **`state-template.json` 完全未被校验** | 高 | 这次 T1 的偏差，校验器本应捕获而未能捕获 |
| `tuning.currencies` / `cultivation` / `time` 子结构未校验 | 中 | 只校验了 `fatigue` 与 `actions` 的存在性 |
| `tuning.actions` 每个条目的结构未校验 | 中 | 只检查了是不是对象 |
| starter 引用的 `locationId` / `regionId` 引用完整性未校验 | 中 | 悬空引用 |
| 缺字段检测（存在性反向检查） | 高 | 目前只查"该有的有没有"，不查"**不该少的少没少**"，所以 T1 丢 5 个字段无人报警 |

**要求**：

1. 新增 `validateStateTemplate()`
2. 对 `tuning` 各子结构做逐字段类型校验
3. **新增必填字段清单（required fields）反向检查**——这是能自动抓住 T1 类问题的唯一手段
4. starter 的 location/region 引用与 `world.json` 做完整性校验
