## 3. ⚠️ 5.3 只完成一半：文字去掉了，**进度条还在**

### 事实

`《11 报告》§2.3` 第 2 点自己写明了：

> 进度条宽度折算：`Math.min(100, (char.progressInternal / maxCultivation) * 100)`

对应 `app.js:202-207` 与 `styles.css`：

```js
const track = document.createElement("div");   // L202
track.className = "progress-track";
const fill = document.createElement("div");    // L204
fill.className = "progress-fill";
fill.style.width = Math.min(100, Math.max(0, (progressNum / maxCultivation) * 100)) + "%";  // L206
```

```css
.progress-fill { height: 100%; background: linear-gradient(...); transition: width 0.3s ease; }
```

**这是一条按精确百分比平滑填充的进度条。玩家可以从条的长度直接读出「我现在 45%」。**

### 为什么这是问题（不是吹毛求疵）

设定集 `26_GM_Realm_Progression_Quantification` **第 3 行**原文：

> 目标是让成长可解释、可记录，**而非把修仙简化成经验值刷条**。

**「经验值刷条」正是这条进度条。** 设定集点名的反目标，不是我的个人口味。

再加上 §2 的「不对玩家展示虚假的精确百分比」——**条形长度就是百分比的另一种写法**，只是没写数字。

### 为什么测试没抓到

`tests/no-percentage-ui.test.js` 的检查方式是：

- 扫 `narration.json` 的文本 `%`
- 扫 `index.html` 的文本 `%`
- 扫 `app.js` 中「**用户展示层（排除机器接口）**」的 `%` 格式化

**它扫的是"文本呈现"，不扫渲染路径里的 CSS 宽度计算。** 所以 L206 从它眼皮下过。

### 建议的修法（保留视觉反馈，不泄露精度）

**把连续条改成离散档位**：

- `progress-track` 拆成 **3 段**，按 `progressBand` 点亮（`initial` 亮 1 段 / `marked` 亮 2 段 / `near` 亮 3 段）
- `ready` 时三段全亮并加金边（对应「条件齐备」）
- **去掉 `transition: width` 的平滑填充** —— 平滑填充本身就是"刷条"的手感

这样玩家仍有视觉反馈，但读不出精确百分比。**若 YY 认为连续条可接受，也可以保留 —— 但那是修改设定集口径，需走变更流程。**

## 4. 需要 YY 裁定：经济「净变化 0」是不是你想要的手感

3 日实测：**收入 +5、支出 −5、净变化 0**（起始 10 枚，期末仍是 10 枚）。

数字本身**完全合规** —— 落在设定集 `16` §2「低阶修士一日基础开销 5–20 碎灵」的区间内。

**但后果要你看一眼**：设定集同时规定「简单修炼室一时辰 1–4 枚低阶灵石」。

**净增长为 0，意味着玩家永远攒不到钱用修炼室。** 而修炼室是低阶修士最主要的加速手段。

两种都要得，只能选一个方向：

| 选项 | 做法 | 手感 |
|---|---|---|
| **A · 如履薄冰**（现状） | 维持净 0 | 每一步都紧，但**玩家没有任何积累路径**，容易挫败 |
| **B · 缓慢积累** | 报酬调到 `[2, 3]`，或把基础开销压到 1 灵石/日 | 三日能攒 2–3 枚，**能攒钱但很慢** |
| **C · 靠事件开口子** | 日常维持净 0，**但让探索/委托/人情偶有额外进项** | 最符合设定集「资源会阶段性卡关」的写法 —— **我推荐这个** |

**C 的理由**：设定集 `34_GM_LongTerm_Progression_and_Softlock_Guardrails` 明确写了「普通角色能成长但进度偏慢；**资源会造成阶段性卡关与迷茫**」。净 0 的日常 + 偶发进项，正是"阶段性卡关"而非"永久卡死"。**纯 A 会变成永久卡死。**

**这一条不阻塞 M1，但会影响你的剧本怎么写"主角缺钱"这段戏。** 你想让他怎么翻身——靠探索？靠人情？靠一次冒险？**这直接决定第一卷第一章的冲突。**

## 5. 新发现 N7 · 两个修为字段并存，而新字段不在校验范围

### 事实

| 位置 | 情况 |
|---|---|
| `app.js` L138 / L164 / L751（**读取**） | `char.cultivationProgress !== null ? char.cultivationProgress : char.progressInternal` —— **优先读旧字段** |
| `app.js` L800 / L874 / L920 / L946（**写入**） | `charPatch.cultivationProgress = ...` |
| `app.js` L801 / L875（**写入**） | `charPatch.progressInternal = ...` |
| `state-template.json` | 两个字段都是 `null` |
| `starter.json` | 两个字段**都写成 10** |
| `validate-schema.js` | **含 `cultivationProgress`，不含 `progressInternal`** |

### 问题

1. **双源并存**：同一件事有两个字段。目前靠"两边都写"维持一致 —— **这是脆弱的一致**，任何一条只写一边的路径都会造成静默分叉
2. **读旧、写新**：读取优先用 `cultivationProgress`。**如果哪天只更新了 `progressInternal`，修为就不动了**，而且不会报错
3. **校验器只认识旧字段**：`progressInternal` 完全不在必填清单与校验范围内 —— **新的权威字段反而是无人看守的那个**
4. 这与之前 T1（`state-template` Schema 长歪）、N2（currency 形状）、N5（itemId）**是同一类病**：两处真相并存

### 要求

1. **明确 `progressInternal` 为唯一权威字段**
2. `cultivationProgress` 二选一：**（a）删除**；或 **（b）标为 legacy，并在校验器中断言「若存在，必须与 `progressInternal` 相等」**，M1 前清理完毕
3. 读取逻辑统一为只读 `progressInternal`，去掉 fallback
4. `validate-schema.js` 把 `progressInternal` 纳入必填（与 `realmStability` / `progressBand` 同组）
