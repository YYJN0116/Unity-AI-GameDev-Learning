## 2. 需要 YY 裁定的四个问题

### Q-A · 修为进度到底怎么表示？

| 方案 | 内容 | 评价 |
|---|---|---|
| **1** | 完全按设定集：改为离散状态 `未稳固 / 已稳固 / 积累中（初步·明显·接近）/ 条件齐备 / 突破后待巩固`，**不显示百分比** | 最忠于设定集，但数值架构失去可计算的连续量，事件条件只能靠离散档位组合 |
| **2** | 保留 0–100 百分比 | **与设定集直接对立，不推荐** |
| **3（我推荐）** | **内部分离**：引擎内部保留一个不对外显示的进度量（供条件判定与平衡调参），**界面上只显示离散状态文字** | 注意：设定集禁止的是「**对玩家展示**虚假的精确百分比」，**并未禁止内部使用**。方案 3 不违反设定集，同时保住可计算性 |

**若选方案 3，必须写进规范**：任何 `narration`、结果卡、角色面板**不得出现百分比**。这是硬验收项。

### Q-B · 突破条件：单一进度条，还是条件清单？

设定集 `26` §3 要求 8 维度评估。**我推荐做成可计算的条件清单**——这也正是 Event Node Schema 的 `activation` 条件的天然用法：

```jsonc
"breakthrough.qi.2to3": {
  "activation": { "all": [
    { "gte": ["character.spiritualPower.value", 30] },
    { "lte": ["character.fatigue.value", 40] },
    { "empty": ["character.injuries"] },
    { "gte": ["character.techniqueMastery[technique.tuna].stage", "熟练"] },
    { "flag": "knows.breakthrough.method" }
  ]}
}
```

**好处**：数值只负责其中几项，其余用条件表达。「按情境判定」就落成了「条件清单」，引擎可执行，且**完全不需要伪精确百分比**。

**代价**：编剧侧要为每个层次写一张条件清单（10 个层次 × 若干条件）。这是真实工作量。

### Q-C · 检定：单一属性 vs DC，还是多因素修正？

**我承认原 Q1 方案太薄。** 设定集列了 12 项。

**我推荐**：基础式仍是 `1d10 + 主属性评级 vs DC`，但允许**一组有限修正**：

| 修正来源 | 范围 |
|---|---|
| 充分准备 / 可靠情报 / 有利地形 / 先手 / 人数优势 | 各 **+1** |
| 带伤 / 心神不宁 / 环境恶劣 / 被围 | 各 **−1** |
| **总修正上限 ±3** | 防止变成算表游戏 |

超出这个范围的因素（如大境界差距）**不进修正，直接进条件**——例如「筑基修士面前，炼气期的正面强攻选项直接不可选（`requires` 不满足）」。**这才是设定集「跨境能力差必须真实存在」的正确实现方式。**

### Q-D · 物价：跟设定集，还是跟现状？

| | 丹药价格 | 后果 |
|---|---|---|
| 现状 | 6 枚低阶灵石 | 差使一次赚 3–8 灵石 → 「干两天活买一颗药」 |
| 设定集 | 0.5–2 枚低阶灵石 | 同样收入 → 「干半天活买一颗药」，**经济明显变松** |

**我推荐跟设定集**——它是你 41 份文档里亲手定的口径，现状那 6 枚是旧 AI 随手写的。

**但你要知道这改变了手感。** 你可以选：
- **跟设定集**（推荐），同时**下调差使报酬**来保持紧张感
- 或**保留 6 灵石**，那就得改设定集——但那是修订正史，要走变更流程

## 3. 四份交付物的字段草案

### 3.1 数值基线 v0.2 · 字段草案

**（待交付）** 状态层新增/修订字段：

| 字段 | 类型 | 单位 / 量表 | 说明 |
|---|---|---|---|
| `character.realm` | object | — | 沿用现有 `{name, level, stage}` |
| `character.realmStability` | enum | — | **新增**：`unstable` 未稳固 / `stable` 已稳固 / `accumulating` 积累中 / `ready` 条件齐备 / `consolidating` 突破后待巩固（依据 `26` §2） |
| `character.progressBand` | enum | — | **新增**：`initial` 初步 / `marked` 明显 / `near` 接近（仅当 `realmStability = accumulating`） |
| `character.progressInternal` | number \| null | `scaleId:"internal"` | **新增（仅当 Q-A 选方案 3）**：内部进度量，**不得显示给玩家** |
| `character.spiritualPower` | object | `unit` 必填 | 沿用 `{value, unit, controlState}`；**上限规则需按境界定义，不得再用 `层数 × 15`** |
| `character.spiritualPowerControl` | enum | — | **新增**：`steady` 平稳 / `fluctuating` 波动 / `disordered` 紊乱（依据 `16` §5「灵力紊乱与外伤分开记录」） |
| `character.fatigue` | object | `scaleId` 必填 | 沿用 `{value, scaleId, description}`；阈值与文字档位写入 `tuning.json` |
| `character.techniqueMastery` | array | — | **新增（C-7）**：`[{techniqueId, stage, evidence:[]}]`，`stage` 取 `未接触/初识/入门/熟练/精通/自成体系`（依据 `12` §1） |
| `character.understanding` | array | — | **新增（C-7）**：`[{topicId, level, evidence:[]}]`，记录对原理/功法/局势的理解（依据 `12` §1） |
| `character.injuries` | array | — | 扩展为 `[{id, part, severity, restriction, treatment, recoveryWindow, worseningCondition, sequelRisk}]`（依据 `16` §5 八项必记） |
| `character.soulLoad` | object | — | **新增**：神识负荷，与疲劳、外伤**分开记录**（依据 `16` §5） |

**明确不做**（写入规范作为禁止项）：

- ❌ 全局生命值 `health`
- ❌ 全局经验值 / 修为点数
- ❌ 任何形式的「单一数字代替角色能力」（`26` §1.2 明文禁止）
- ❌ 界面展示精确百分比（若 Q-A 选方案 1 或 3）
- ❌ 固定天数自动升级

### 3.2 检定属性层 · 字段草案

**这一层的存在理由**：设定集要求「不以单一数字代替角色能力」，同时引擎需要可计算的判定量。**属性层是那五个维度的可计算投影，不是替代品。**

| 属性 | 覆盖设定集的哪个维度 | 推导来源 |
|---|---|---|
| `daohang` 道行 | 境界 | `realm`（大境界 + 小层次） |
| `lingli` 灵力 | 灵力基础 | `spiritualPower.value` 相对当前境界上限的比值 + `controlState` |
| `shenshi` 神识 | 身体/神魂状态 | 境界 + `soulLoad` + 心志类状态 |
| `shenfa` 身法 | 身体/神魂状态 | `constitution` + `injuries` + `fatigue` |
| `wuxing` 悟性 | 理解与经验 | `understanding` 条目数/深度 + `spiritualRoot` |
| `xinzhi` 心志 | 身体/神魂状态 | 心境标记 / flag（如「道心坚定」） |

**取值**：每项 1–5 评级（1 拙劣 / 2 平平 / 3 尚可 / 4 出色 / 5 卓绝）。

**关键约束**：
- 评级**由状态推导，不独立存储**（避免第二套真相与漂移）
- 推导规则写入 `tuning.json`
- **大境界差距不用属性表达**，用条件门控（见 Q-C）

### 3.3 DC 难度基线表 · 字段草案

| 档位 | DC | 语义 | 典型情境 |
|---|---:|---|---|
| 轻而易举 | 5 | 稍有经验即可 | 日常操作 |
| 简单 | 7 | 正常水平可完成 | 熟练技艺的常规运用 |
| 常规 | 9 | 需真正能力 | 有压力的对抗 |
| 困难 | 11 | 需专长或有利条件 | 越级尝试 |
| 险峻 | 13 | 需专长 **且** 有利条件 | 明显不利局面 |
| 近乎不可能 | 15 | 只有卓绝 + 修正拉满 | 极罕见 |

**配套规则**：
- 修正项：每项 ±1，**总上限 ±3**
- **自然 10（大成功）/ 自然 1（大失败）**：是否保留需你裁定
- **失败前进（fail-forward）**：Q2 已定采纳。规范里要写明：`onFail` **必须**给出可继续的 `next`，或明确写出「失败但不推进」的理由
- `check` 缺失时：该选项**不掷骰**，直接按 `effects` 结算（日常行动不该每次都掷）

### 3.4 Event Node Schema 定稿 · 相对 v1 §6.2 的增量

沿用《交接报告 v1》§6.2 的全部字段，**新增/修订如下**：

| 变更 | 内容 |
|---|---|
| **新增效果操作符** | `technique.gain`（提升技艺阶段）、`understanding.set`、`soul.load`、`injury.add`（扩展为八字段） |
| **新增条件操作符** | `empty`（列表为空）、`realmStability`、`techniqueStage`、`understandingLevel` |
| **`check` 扩展** | 新增 `modifiers: [{source, value}]`，总修正上限 ±3 |
| **多 main 冲突** | 同一 tick 多个 `main` 命中 = **校验错误**（不是运行时消解） |
| **`defaultOutcome`** | **必填**，防软锁 |
| **`kind` 语义** | `main` 无条件抢占；`side` 条件匹配；`ambient` **种子化加权随机** |
| **禁止项** | 任何节点不得要求玩家做出超出其已知信息的判断（依据 `02` §4 认知边界） |
