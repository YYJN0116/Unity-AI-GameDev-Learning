### 1.4 数值口径处于「文档与代码互相打脸」状态

[`策划与世界观设计文档/v0.1-data-standard.md`](策划与世界观设计文档/v0.1-data-standard.md) 第 119 行的原文规定：

> 修为进度、灵力、疲劳、伤势、神识负荷｜**项目没有全局数值单位、上限或阈值；不得默认使用 `health=100` 之类的隐含规则。**
> 人情、名声、关系、债务｜**不折算成通用点数**

而实际代码在做：

- 修为按 0–100 百分比推进，满 100 触发突破（`app.js:808`、`app.js:916`）
- 疲劳 0–100，用 40 / 70 两档阈值切文字描述（`app.js:809-811`）
- 灵力上限 = 炼气层数 × 15（`app.js:921`）
- 采集 / 交易 / 战斗全部是硬编码随机区间（`app.js:835-1025`）

同时，交接指南 §5.1 的示例状态又出现 `affinity: 25`、`vitality: {current, max}`、`spiritRoots: [...]` —— **这三项 v0.1 明确禁止**。

**结论：v0.1 是「无固定数值的自由叙事」口径，与 Gamebook 玩法不兼容。** Gamebook 的乐趣核心是「我这条选择能不能过」，没有可计算判定就没有游戏。因此 v0.1 不再修补，直接发布 v0.2（见 §6.1）。

## 2. 结论

1. **叙事架构**：采用混合模式 —— 主线用章节节点树做骨架（控制伏笔、宿命感、结局），日常与支线用状态驱动事件池做血肉（提供自由度与重玩度）。**统一为单一 Event Node Schema，用 `kind: "main" | "side" | "ambient"` 区分**。
2. **引擎现状**：事件层契约为零。`world.events` 是空壳，玩家输入无机制效力，全部内容硬编码在 `app.js`。**这不是「填充内容」能解决的，必须先打地基。**
3. **本次改造的定性**：**内容与代码分离** + **建立事件管线** + **建立世界时间轴**。属于下层建筑重构，不改变已实现的 UI 与存档流程外观。

## 3. 已定决策（YY 拍板，Antigravity 无需再讨论）

| ID | 决策 | 说明 |
|---|---|---|
| **D1** | 叙事架构 = 混合模式 C | main / side / ambient 三类节点，单一 Schema |
| **D2** | 好感度不做连续数值 | 改为离散阶段（陌生 / 相识 / 信赖 / 生死之交）+ 因果记录。理由：连续好感度在网状剧本中会造成分支爆炸，且无法向玩家解释数值来源。数值化字段限于：修为进度、灵力、疲劳、灵石、物品数量、时间 |
| **D3** | 世界自走 = 真做 | 玩家不介入时事件仍按时间轴发展。需要 tick 调度器，工程量较大，接受 |
| **D4** | 世界观重写 | 正史未定。**引擎必须对内容完全无感**，不得把任何现有世界观名称写进代码 |
| **D5** | 存档不兼容 | v0.1 存档不作兼容，允许破坏性变更（项目尚无真实玩家存档），更换 `STORAGE_KEY` 并写入版本号 |

## 5. 引擎改造需求清单

### R1 · 内容与代码彻底分离 ⭐ 最高优先级

**要求**：把 `app.js` 内的所有世界观内容、叙事文本、数值常量、事件定义全部外移到独立数据文件。

- `app.js:12` 的 `WORLD_DATABASE` → `data/world.json`
- `app.js:190-207` 的初始状态模板 → `data/state-template.json`
- `app.js:504-558` 的新手开局角色 → `data/starters/*.json`
- `app.js:786-1053` 的所有 `narration` 字符串与随机区间 → `data/events/*.json` + `data/tuning.json`
- `app.js:7-11` 的 `ACTIONS` 保留为引擎枚举，但**行动的内容表现（叙事、耗时、数值）必须来自数据**

**验收**：新增一个事件、改一个数值、换一套世界观，**不需要改任何 `.js` 文件**。引擎代码中不出现任何具体地名、人名、势力名、功法名。

**理由**：YY 正在重写正史。只要内容还留在代码里，每改一次设定就要改一次代码，两边必然失同步。

### R2 · Schema 校验器

**要求**：一个可独立运行的校验脚本（Node），校验所有 events / tuning / world / starter 文件。

- 必须报告 **event id + 字段路径 + 违规原因**，不能只报「校验失败」
- 必须在 E2E 测试之前跑，失败即阻断

**验收**：故意写一个非法节点，校验器准确指出是哪个 event 的哪个字段。

### R3 · 事件加载与索引

**要求**：启动时加载全部事件，建立索引：

- by id（唯一性检查）
- by kind
- by region / location
- by activation 依赖的 flag（用于快速筛选可触发集合）

**验收**：重复 id 直接报错终止；孤儿引用（`next` 指向不存在的 id）在校验阶段被捕获。

### R4 · Condition DSL 解释器

**要求**：白名单操作符，**禁止 `eval` / `new Function` / 任何动态代码求值**（这是开源项目与 GitHub Pages 部署的硬性安全要求）。

- 未识别的操作符必须**报错**，不得静默返回 `false`（静默失败会让编剧以为条件生效了，是最危险的 bug 类型）
- 求值失败的字段路径必须报错定位

**验收**：`{"op": "summon_demon"}` 这类未知条件在加载时即报错。

### R5 · Effect DSL 执行器

**要求**：全部状态变更走命名操作符（见 §6.4），并且：

- **每一次 effect 都必须写一条 `ledger` 记录**（`before` / `change` / `after` / `reason` / `确定程度`），沿用现有 ledger 结构
- 数值不得越界（灵石、物品数量不得为负；疲劳钳制 0–100；修为钳制 0–100）
- 钳制发生时必须在 ledger 中标注

**验收**：跑 100 次随机行动，`ledger` 可完整复算出现有状态。

### R6 · 触发管线与优先级

**要求**：

- `main` 节点：条件满足即**抢占**，优先级最高，同一 tick 只能触发一个主线节点
- `side` 节点：按条件筛选，优先级次之
- `ambient` 节点：按权重随机，优先级最低
- 同一 tick 内多个候选时的消解规则必须**确定性可复现**（不得依赖对象遍历顺序）
- `once: true` 的节点触发后永久不再触发
- `cooldownDays` 生效

**验收**：构造多个节点同时满足条件的用例，验证抢占顺序与可复现性。

### R7 · 世界时间轴调度器（对应 D3）

**要求**：

- 行动推进时间时，除结算玩家行动外，**同时推进世界状态**
- 世界状态推进必须是**幂等且可复现**的：同一存档 + 同一段时间推进 → 同一结果
- 玩家不在场的世界变化要能写入 `world.offstageLog`，供玩家事后通过线索发现（这是 09 号事件网「不介入也照常发展」的实现基础）
- 禁止「为了挽留剧情而强行让已缓和的事件再次恶化」——这是 09 文档明确规定的守护规则，需在代码层面留注释说明

**验收**：连续推进 30 天，事件按预期演化，且读档重放结果一致。

### R8 · 种子化随机

**现状问题**：全代码使用裸 `Math.random()`，**读档后随机序列不可复现**，Gamebook 的判定结果无法回放、无法写测试。

**要求**：引入 seeded RNG，种子存于 `state.rngSeed`，所有随机数经由该 RNG。存读档后继续推进，结果必须与未存读档时一致。

**验收**：固定种子 + 固定输入序列 → 输出完全一致（可写成断言测试）。

### R9 · 存档版本与迁移

**要求**：`schemaVersion` 升到 `0.2`，更换 `STORAGE_KEY`。加载到旧版本存档时给出**明确提示**（例如"此存档为旧版本，本版不兼容"），不得静默读入半坏的存档。

**验收**：手动写入一份 v0.1 存档，加载时得到明确提示且不污染当前状态。

### R10 · UI 支撑

**要求**：

- **选项按钮化**：Event Node 的 `choices` 渲染为按钮，显示 `label`、可用/不可用状态（`requires` 不满足时置灰并显示原因）
- **判定结果卡**：展示属性、骰值、DC、评级
- **叙事与机制分离展示**：叙事文本归纪事流，数值变化归结果卡（现有结构已支持，复用即可）
- **章节感**：main 节点触发时给章节标题以视觉层级

### R11 · 玩家自由输入的定位

**现状**：自由输入对机制零影响（F2）。这在 Gamebook 模式下是设计缺陷。

**要求**（**此处需要 YY 最终确认**）：

- **默认方案**：主线与支线走**显式选项**；自由输入保留为「氛围描述」，仅在极客模式（LLM 导出）中具备机制意义，UI 上必须明确提示玩家这一点，不得误导
- 若 YY 要求自由输入参与判定，则需要额外设计「意图识别 → 映射到选项」层，工程量另计，**不建议在 M1 阶段做**

## 6. 接口草案（DRAFT v0.1 — 待三方审）

### 6.1 数值基线 v0.2（取代 v0.1 的「无数值」口径）

| 字段 | 单位 / 量表 | 范围 | 说明 |
|---|---|---|---|
| `character.cultivationProgress` | `scaleId: "0-100"` | 0–100 | 满 100 **不自动突破**，仅解锁突破判定的资格 |
| `character.spiritualPower.value` | `unit: "缕"` | 0 – 上限 | 上限由境界表定义，**不得再用 `层数 × 15` 这种散落在代码里的公式** |
| `character.fatigue.value` | `scaleId: "0-100"` | 0–100 | 40 / 70 为文字档位阈值，阈值写入 `tuning.json` |
| `currencyBalances[].unit` | 机器 id：`lowGradeSpiritStone` / `fragment` | ≥ 0 | **现有代码用的是显示名「下品灵石」，必须改为机器 id + 独立显示名映射表** |
| `inventory[].quantity` | 数量 + `unit`（株/卷/枚） | ≥ 0 | 必须有 `itemId` |
| `relationships[]` | `stage` 枚举 + `cause` 字符串 | — | `stranger` / `acquainted` / `trusted` / `sworn`；**不折算点数** |
| `updatedAt.timeOfDayMinutes` | 分钟（整数） | 0–1439 | 沿用现有换算（1 时辰 = 120 分钟） |
| `injuries[]` | 结构体列表 | — | 与疲劳分离，沿用 v0.1 的「不与生命值混用」原则 |

> 全部阈值与公式集中写入 `data/tuning.json`，**代码中不得出现魔法数字**。

### 6.2 Event Node Schema（草案）

```jsonc
{
  "id": "main.ch01.01",              // 全局唯一，命名规范：kind.chapter.序号
  "kind": "main",                     // main | side | ambient
  "title": "坊市口的争执",
  "chapter": 1,
  "region": "region-id",
  "location": "location-id",
  "once": true,
  "cooldownDays": 0,
  "weight": null,                     // 仅 ambient/side 使用

  "activation": {                     // WHEN：何时可被触发
    "all": [
      { "gte": ["character.realm.level", 1] },
      { "flag": "met.old-herb-gatherer" },
      { "timeBetween": [480, 1080] }
    ]
  },
  "invalidation": { "any": [ { "flag": "ch01.ended" } ] },
  "scene": {
    "text": "……叙述正文……",
    "speaker": null
  },

  "choices": [
    {
      "id": "a",
      "label": "上前劝架",
      "requires": { "gte": ["character.spiritualPower.value", 2] },
      "check": {
        "stat": "character.spiritualPower.value",
        "dice": "1d10",
        "dc": 8
      },
      "onSuccess": { "effects": [], "next": "main.ch01.02a" },
      "onFail":    { "effects": [], "next": "main.ch01.02b" }
    }
  ],

  "defaultOutcome": { "effects": [], "next": null }   // 所有 choice 都被 requires 关掉时的兜底，必填以防软锁
}
```

### 6.3 Condition DSL（白名单操作符）

**逻辑**：`all` / `any` / `not`
**比较**：`eq` / `ne` / `gt` / `gte` / `lt` / `lte`（`[path, value]`）

**专用条件**：

- `flag`：某 flag 是否为真
- `hasItem` / `countItem`：`[itemId, n]`
- `relationStage`：`[npcId, stage]` + 可选比较符
- `locationIs` / `regionIs`
- `day` / `timeBetween`：`[min, max]`
- `eventFired` / `eventNotFired`：`[eventId]`
- `taskActive`：`[taskId]`

**规则**：路径求值失败 = **报错**，不是 `false`。未识别的操作符在**加载阶段**就报错。

### 6.4 Effect DSL（命名操作符）

```jsonc
{ "op": "stat.add",      "stat": "character.cultivationProgress", "delta": 5, "reason": "静修吐纳" }
{ "op": "stat.set",      "stat": "character.fatigue.value", "value": 60, "reason": "长时赶路" }
{ "op": "currency.add",  "unit": "lowGradeSpiritStone", "amount": -3, "reason": "购买伤药" }
{ "op": "item.add",      "itemId": "qi-gathering-herb", "quantity": 1, "reason": "采药所得" }
{ "op": "item.remove",   "itemId": "qi-gathering-herb", "quantity": 1, "reason": "炼丹消耗" }
{ "op": "relation.set",  "npcId": "old-herb-gatherer", "stage": "trusted", "cause": "代为送药" }
{ "op": "flag.set",      "flag": "met.old-herb-gatherer", "value": true }
{ "op": "time.advance",  "minutes": 120 }
{ "op": "location.move", "locationId": "herb-valley" }
{ "op": "injury.add",    "id": "meridian-strain", "severity": "minor", "cause": "强行冲关" }
```

**要求**：每个 effect 执行后**立即写 ledger**。

### 6.5 状态结构需要新增的字段

| 字段 | 类型 | 用途 |
|---|---|---|

## 9. 风险

1. **文档重复与漂移**：`04 / 05 / 19 / 23 / 36` 在 `xiuxian_working_v1.5/` 与 `xiuxian_player_safe_pack_v1.5/` 中重名。已核对：`04`、`19`、`23`、`36` 字节一致，但 **`05_Live_Save_Template.md`（2932 字节）与 `05_Player_Safe_Live_Save_Template.md`（2799 字节）已经不同**。建议明确单一来源，另一处只做发布用副本。
2. **叙事质量风险**：硬编码叙事（如 `app.js:901`、`app.js:924`）文风尚可，但长短不一、信息密度不均。外移到数据后必须建立统一的叙事写作规范，否则事件库会变成文风杂烩。
3. **工作量风险**：R7（世界自走）是本次最大的不确定项。建议 M2 单独排期并先做技术验证，不要与内容生产并行。
4. **接口风险**：若编剧侧在 Schema 冻结前开始大量生产，会产生大批需要返工的事件 JSON。**建议 M1 完成前，编剧侧只产出一份不超过 5 个节点的试样本。**
