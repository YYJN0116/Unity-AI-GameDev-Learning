## 3. 不接受「闭环」的三条理由

### R1-1（严重）· 自查方法被设计成必然通过

《06 报告》T5 的自查是：

> 在 `app.js` 内全文检索「大陆 / 宗 / 洞府 / 老叟 / 少年 / 陆青云 / 采药老叟 / 孙老」，命中结果为**严格 0 处**

**这个检查必然通过，因为它只搜专有名词。** 把「少年陆青云独居于后山洞府」改写成「你在静室之中运转周天」，专有名词归零，但**那仍然是写在代码里的内容文本**。

R1 的验收标准从来不是「不含专有名词」，而是《交接报告 v1》R1 原文：

> **新增一个事件、改一个数值、换一套世界观，不需要改任何 `.js` 文件。**

**用这个标准衡量，当前 `app.js` 一项都不满足。**

建议把自查标准换成可机械执行的反向验证：**随机挑一个数值（例如 fatigue 阈值）与一段文案，只改数据文件、不改任何 `.js`，重跑游戏确认生效。** 做不到就是没闭环。

## 4. 新发现的两个缺陷

### N1（玩家可见）· 左栏灵石显示成机器 ID

**现象**：`app.js` 第 115 行的渲染路径是

```js
(item.unit || "灵石") + " " + formatValue(item.amount)
```

M0 之后 `currencyBalances[].unit` 已改为**机器 ID**（`lowGradeSpiritStone`）。因此左栏「💎 随身灵石」实际会显示：

```
💎 随身灵石    lowGradeSpiritStone 10
```

**M0 之前显示的是「下品灵石 12」，这是一个可见的显示回归。**

**而数据就在手边没被使用**：`tuning.json` 里已经写了

```json
"lowGradeSpiritStone": { "displayName": "下品灵石", "displayUnit": "枚" }
```

**要求**：渲染时按 `TUNING.currencies[unit].displayName` 解析，`unit` 只作机器键，**永不出现在界面上**。

验收：跑一局，左栏显示「下品灵石 10」，界面任何位置不出现 `lowGradeSpiritStone` 字样。

### N2 · 校验器禁止的字段，引擎自己在写

`《06 报告》T4` 声称校验器「**严密检查并禁止**出现 `character.vitality`、`character.spiritRoots` 数组或 **`currencyBalances[].currency`**」。

但 `app.js` 第 742 行运行时在写：

```js
currencies.push({ currency: "下品灵石", unit: "lowGradeSpiritStone", amount: found });
```

**引擎自己生产了校验器明令禁止的字段。**

原因：校验器只检查 `state-template.json` 与 `starters/*.json` 等**静态文件**，不检查引擎运行时生成的状态。**于是这道防线被引擎自己的代码绕过去了。**

而 `starters/placeholder-starter.json` 里是正确的 `{ unit, amount }`——**数据文件对、代码错，两边不一致**。

**要求**：

1. `app.js` 改为写入 `{ unit: "lowGradeSpiritStone", amount: found }`，读取时只按 `unit` 匹配
2. **新增运行时状态校验**：存档前（或 save/load 流程中）对当前 `state` 跑一次同一套字段校验。否则「校验器」只能保证模板正确，保证不了真实存档正确
3. 验收：跑一局 → 保存 → 导出 JSON，`currencyBalances` 条目为 `{ unit, amount }`，无 `currency` 字段

### N3（小）· AI 提示词模板里的 schemaVersion 还是 0.1

`app.js` 第 1047 行的提示词模板：

```
'{"schemaVersion":"0.1","result":{...},"statePatch":{}}'
```

存档 schemaVersion 已于 M0 升至 `0.2`。这是给玩家看的提示词，应当一致。

### N4（新增，2026-10-16 复核时发现）· 种子化随机只做了一半

**`Math.random()` 与 `nextRandom()` 在同一个文件里并存：**

| 位置 | 现状 |
|---|---|
| `app.js:737` `const found = Math.floor(nextRandom() * 4) + 2;` | ✅ 已用种子化 RNG |
| `app.js:387` `getRandomEligible()` → `eligible[Math.floor(Math.random() * eligible.length)]` | ❌ **仍是裸 `Math.random()`** |

**影响**：R8 的验收标准是「同种子 + 同输入 → 结果完全一致」。凡经过 `getRandomEligible()` 的路径（随机世界 / 角色生成）**不受种子控制，读档复现必然失败**。

**说明**：R8 本属 M1 范围，**《07 报告》不将其判为 M0 缺陷**。但既然 `nextRandom()` 已经引入，**混用比全用 `Math.random()` 更危险**——它会让人误以为随机已可控，直到 M1 的复现测试挂掉才暴露。

**要求**：在 M1 开始前统一收口到单一 RNG 入口（全部随机数经由 `nextRandom()`），并补一条断言测试：固定种子 + 固定输入序列 → 输出完全一致。

## 5. 建议的落地方式（规格，非实现）

把 R1 剩余部分外移，建议拆成**两个文件、两类内容**——**数值与文案必须分开**，理由见下：

**① `data/tuning.json` 扩展数值侧**

```jsonc
"actions": {
  "cultivate": {
    "timeCostMinutes": 120,
    "label": "修炼",
    "fatigueGain": 12,
    "outcomes": [
      { "id": "cultivate.progress", "weight": 80, "narrationKey": "action.cultivate.progress",
        "effects": [ { "op": "stat.add", "stat": "cultivationProgress", "delta": "6-11" } ] },
      { "id": "cultivate.full",     "weight": 20, "narrationKey": "action.cultivate.full",
        "effects": [ { "op": "stat.add", "stat": "cultivationProgress", "delta": "0" } ] }
    ]
  }
}
```

**② `data/text/narration.json` 收纳全部文案**

```jsonc
{
  "action.cultivate.progress": "你在{location}之中运转周天吐纳天地灵气……（+{gain}%）",
  "action.explore.herb":       "你在{location}周边细细寻查，在石缝中发现了一株……【{itemName}】……"
}
```

占位符由引擎替换，**文案本身不含任何逻辑**。

**为什么数值与文案必须分文件**：

1. 数值是**策划与数值架构**的产出（小肥负责），文案是**编剧**的产出（YY 负责）——**两个人的工作不该挤在同一个文件里互相冲突**
2. 改一个数值不该让文案文件的 git 历史变脏，反之亦然
3. 将来若要做多语言或文案替换，只需替换 text 层

**物品同理**：`item.wild-herb` / `item.qi-pill` 这类应进 `data/items/*.json`（id、名称、单位、参考价、可用途），引擎只引用 id。
