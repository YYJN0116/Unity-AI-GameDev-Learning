收到。这个背景会改变我对仓库的判断：**这是“小说正史 + 离线游戏玩家线”的双作品项目，不是一个单独的游戏原型。**

而且你对 GM 规则的定位是对的：在纯离线模式下，它们不是给 AI 临场发挥的提示，而是 **事件数据、条件、效果和世界状态之间的接口契约**。对引擎来说，规则文档就相当于 API 规范和数据协议。`data/events/` 为空，意味着当前真正缺的不是“填剧情”，而是还没有完成从规范到运行时的第一条闭环。

## 先给结论

### 1. 双线设计原则上跑得动，但当前引擎还不能直接承载

“小说主角走一条线，玩家走另一条线，重大事件汇合”这个结构是可行的，甚至很适合你现在的架构：

```text
小说主角线：固定正史时间线
        │
        ├── 重大事件锚点
        │
玩家角色线：地点、行动、关系、认知、局部选择
        │
        └── 在指定条件下观察、介入或错过重大事件
```

但当前代码只能部分支持：

- 已有 `flags`
- 已有 `world.events`
- 已有 `offstageLog`
- 已有 `simulatedThrough`
- 已有 `world.currentLocationId`
- 已有确定性随机数和存档
- 已有 `main / side / ambient` 的设计分类

这些是基础材料，但**还没有真正的事件加载器、事件索引、Condition DSL、Effect DSL 和世界调度器**。仓库文档自己也明确写过：事件层目前仍是空壳，实际行动内容仍然大量硬编码在 `app.js`。

所以我的判断是：

> **叙事模型能跑，现有实现还跑不了完整模型。**
>
> 目前最容易跑通的是“玩家触发事件 → 做选择 → 修改玩家状态 → 进入下一个节点”。  
> 最容易卡住的是“小说主角独立行动 → 世界时间推进 → 玩家不在场时事件继续发展 → 玩家之后看到事件后果 → 重大事件按固定正史汇合”。

# 一、双线结构在工程上哪里会卡

## 1. 当前只有“玩家状态”，没有“世界状态时间线”

现在的 `state` 主要描述：

```text
character
gameWorld
world.currentLocationId
world.events
ledger
flags
rngSeed / rngCursor
updatedAt
```

但双线结构至少需要区分三种东西：

```text
A. 世界正史时间线
   小说主角和重大事件按固定顺序发生

B. 玩家局部状态
   玩家在哪里、知道什么、与谁接触、做过什么

C. 世界当前可观察状态
   玩家此时看到什么、哪些事件已经发生、哪些已经错过
```

如果把小说主角直接当成一个普通 NPC，只依赖玩家在场时触发，就会出现严重问题：

- 玩家没去某地，小说主角的事件不推进
- 玩家先去了现场，事件被错误地提前触发
- 玩家改变了一个局部条件，导致固定重大事件被意外改写
- 玩家存档读档后，小说主角线和玩家线无法重新对齐
- 玩家错过事件后，系统不知道应该显示“已发生的后果”，还是重新给他机会

因此，小说主角线不能只放在 `data/npcs/` 里。至少需要一个**正史事件时间轴或世界事件轨道**。

可以抽象成：

```text
canonTimeline
  - canon event A
  - canon event B
  - canon convergence point C
  - canon event D
```

玩家事件则通过：

```text
activation
observation
intervention
consequence
```

与正史时间线发生关系。

---

## 2. “重大事件固定”与“玩家可以影响局部结果”必须分层

你已经明确：

- 重大走向固定
- 玩家不能改变关键人物结局
- 游戏剧情跟着小说走
- 玩家可以走自己的线
- 最终在重大事件处汇合

那事件系统不能把所有选择都设计成传统的“多结局分叉”。应该分成三层：

### A. 不可变正史层

这是小说确定的内容：

```text
小说主角是否到达某地
某重大事件是否发生
某人物是否死亡、离开、背叛或完成某件事
重大事件最终结果
```

这些应该由 `canon` 或 `fixedOutcome` 一类的数据表达。

### B. 玩家可影响的局部层

玩家可以改变：

```text
自己是否提前知道
自己是否在现场
自己是否帮助某个局部人物
自己与某个 NPC 的关系
自己是否获得某个物品或任务状态
自己在重大事件中的观察角度
自己是否遭遇事件的次生影响
```

这些可以写入玩家状态、关系、flag、ledger。

### C. 汇合层

重大事件节点不因为玩家选择而改写正史，而是根据玩家状态决定：

```text
玩家看到什么
玩家能不能介入某个局部环节
玩家能否提前做准备
玩家承担什么代价
玩家事后得到哪些信息
玩家的关系和资源如何变化
```

也就是说，汇合节点更像：

```text
固定世界事件 + 玩家视角分支
```

而不是：

```text
玩家选择 A → 改写小说主线
玩家选择 B → 进入另一条世界正史
```

这是现有 `main / side / ambient` 分类可以承载的，但需要给 `main` 事件增加明确的“正史锚点”语义。

---

## 3. “理解等级”和事件 flag 可以工作，但不要把它们混成证据系统

你说得很重要：项目中没有“证据池”“证据持有率”，也不能用百分比表示玩家掌握程度。

可以保留两类不同状态：

### 对话题的理解等级

例如：

```text
unknown
heard
understood
confirmed
misunderstood
```

具体枚举必须以你的正式规则为准，这里只是说明结构。

它回答的是：

> 玩家对某个话题理解到什么程度？

### 事件 flag

例如：

```text
event.main.ch01.01.started
event.main.ch01.01.observed
event.main.ch01.01.resolved
npc.someone.trust.gained
world.location.market.disturbance
```

它回答的是：

> 某件事是否发生过、是否被处理过、是否改变了世界状态？

二者不要混为：

```text
理解等级 ≠ 证据数量
理解等级 ≠ 百分比
理解等级 ≠ 真相完成度
```

事件条件可以同时检查：

```text
话题理解等级达到某个离散层级
某个事件 flag 已存在
玩家在指定地点
某 NPC 关系达到某个离散状态
```

这样能支持小说线和玩家线汇合，而且不会引入你明确禁止的“证据进度条”。

---

## 4. 当前 AI JSON 接口不能成为离线游戏的核心事件接口

现在 `app.js` 仍然保留了“生成 AI 主持提示词、粘贴 AI 返回 JSON、校验并应用”的能力。这可以作为：

- 开发工具
- 调试工具
- GM 辅助工具
- 极客模式
- 内容测试工具

但不能作为纯离线游戏运行时的依赖。

离线游戏真正的运行路径应该是：

```text
data/events/*.json
        ↓
build-data.js
        ↓
事件索引
        ↓
Condition DSL 求值
        ↓
玩家选择
        ↓
Check / 固定判定
        ↓
Effect DSL 执行
        ↓
ledger
        ↓
存档
```

AI JSON 路径最多是另一条旁路：

```text
AI 输出 JSON
        ↓
严格校验
        ↓
开发者确认
        ↓
测试或调试存档
```

不能让离线模式的剧情依赖 AI 生成内容，否则就违背项目最重要的前提。

---

# 二、第一个事件节点应该怎么落地

不要直接写一个“完整的第一章剧情节点”然后期待引擎接住它。这样返工概率很高。

正确顺序是：**先用一个极小的垂直切片，把接口、加载、条件、效果、存档、回放全部打通。**

## 阶段 0：先冻结事件接口，而不是先写剧情

先从现有规范中冻结这些东西：

### 事件最小身份字段

```text
id
kind
chapter
region
location
once
```

### 事件激活字段

```text
activation
```

### 事件展示字段

```text
scene
choices
```

### 选项逻辑字段

```text
requires
check
onSuccess
onFail
next
```

### 效果字段

```text
effects
```

### 正史相关字段

这里是双线项目必须补上的部分，不能直接照搬旧的单游戏模型。至少要明确是否需要：

```text
canonTrack
canonAnchor
timelinePhase
playerIntervention
observationMode
```

具体名称可以调整，但语义必须先定下来。

特别要回答：

1. 这个事件是不是小说正史事件？
2. 它是不是固定发生？
3. 玩家不在场时是否继续推进？
4. 玩家到场时能改变什么？
5. 玩家只能观察，还是能介入局部？
6. 玩家错过后，再次到场看到的是什么状态？

这些问题不解决，事件 JSON 写得越多，后面返工越大。

---

## 阶段 1：先写一个“无剧情价值”的测试事件

第一个节点不应该一开始就写正式小说剧情。

应该先写一个专门验证管线的测试节点，例如：

```text
test.pipeline.01
```

它只验证：

- 事件能被加载
- `id` 能建立索引
- `location` 外键有效
- `activation` 能求值
- 选项能显示
- `requires` 能控制选项
- `flag.set` 能执行
- `next` 能跳转
- `ledger` 能记录
- 重复执行 `once` 能被阻止
- 存档后重新加载仍保持状态
- 相同 seed 下结果一致

这个节点不应该承载小说信息，也不应该写正式世界观。它是协议测试夹具。

---

## 阶段 2：实现最小 Condition DSL

不要一开始实现所有条件。先做最小白名单：

```text
all
any
not
flag
locationIs
```

然后再加入：

```text
relationAxis
understanding
timeBetween
hasItem
attrs
```

重点不是支持多少操作符，而是以下行为必须先固定：

- 未知操作符直接报错
- 路径不存在直接报错
- 类型错误直接报错
- 不允许静默返回 false
- 条件求值结果可被测试复现
- 不允许 `eval`
- 不允许 `new Function`

特别是“未知条件不能静默返回 false”，这对内容生产非常关键。否则编剧以为某个条件生效了，实际事件永远不会触发。

---

## 阶段 3：实现最小 Effect DSL

先实现真正需要支撑第一个测试节点的效果：

```text
flag.set
event.fire
event.invalidate
ledger.write
```

然后才逐步加入：

```text
location.move
relation.set
understanding.set
item.add
item.remove
currency.add
stat.add
stat.set
time.advance
```

每一个 effect 都必须：

1. 读取旧值
2. 执行变更
3. 生成新值
4. 写入 ledger
5. 标记确定程度或变化依据
6. 失败时整体回滚

这里要特别注意：现有 `app.js` 里的 `statePatch` 是“整段字段替换”模式，而未来事件系统的 Effect DSL 是“命名操作”模式。这两套机制不能未经设计直接混用。

建议分开：

```text
外部 AI 调试路径：statePatch
离线事件运行路径：effects
```

二者最终都经过同一个状态校验器和 ledger 层。

---

## 阶段 4：用 3 个节点做最小闭环

当测试节点跑通后，不要立刻批量生产几十个事件。先做一个最小事件链：

```text
test.pipeline.01
        ↓
test.pipeline.02
        ↓
test.pipeline.03
```

覆盖：

- 一个无条件选项
- 一个被 `requires` 隐藏或禁用的选项
- 一个设置 flag 的选项
- 一个因为 flag 改变而开放的后续节点
- 一个失败后仍能继续的路径
- 一个不可重复触发的节点

这一步的目标是证明：

```text
事件图不是只能从 A 跳到 B，
而是能根据状态稳定地走不同路径。
```

---

## 阶段 5：再做第一个正式事件

第一个正式事件最好满足以下条件：

- 只涉及一个地点
- 只涉及少量 NPC
- 不改变重大正史
- 不涉及复杂经济
- 不依赖未实现的高级检定
- 至少有一个玩家选择
- 至少有一个状态后果
- 至少能留下一个后续 flag
- 能在之后被另一个事件观察到

它应该是“玩家线的局部事件”，而不是第一章最大高潮。

推荐的正式落地顺序是：

```text
1. 小说正史时间线先写出该阶段的固定锚点
2. 为玩家线定义一个不会改变正史的局部切入口
3. 写世界事实、人物认知和玩家可知信息
4. 冻结事件 ID、地点 ID、NPC ID、话题 ID、flag 名
5. 写一个事件 JSON
6. 运行 Schema 校验
7. 运行图完整性检查
8. 接入引擎
9. 写对应自动化测试
10. 再写下一个事件
```

不要先写几十个 JSON，最后才让引擎读取。

---

# 三、小说和游戏应该如何共享内容

不建议让小说 Markdown 直接作为游戏运行数据，也不建议让游戏事件 JSON 直接承担完整小说文本。

应该采用“双轨”：

```text
小说侧：
  小说章节
  世界事实
  主角时间线
  固定重大事件
  角色完整心理和叙事

游戏侧：
  EventNode JSON
  Condition DSL
  Effect DSL
  玩家可见文本
  玩家视角分支
  事件后果
```

二者共享的是稳定 ID 和正史锚点：

```text
character ID
npc ID
location ID
faction ID
topic ID
canon event ID
timeline anchor ID
```

例如：

```text
novel.ch01.anchor.market-conflict
main.ch01.player-observe-market-conflict
main.ch01.player-intervene-market-conflict
```

这样小说可以写完整叙事，游戏只实现玩家实际能观察和参与的部分，但二者仍然能确认：

> 这是同一个世界、同一件重大事件、同一条固定正史。

# 四、离线游戏“做庞大一点”合理到什么程度

这里要区分两个上限：

## 1. 技术加载上限

目前项目会通过 `build-data.js` 把数据打包进 `data-bundle.js`，启动时整体加载。这个模式的真正瓶颈不是“文件数量”本身，而是：

- 初始加载时间
- 浏览器内存
- JSON 解析时间
- 事件索引建立时间
- 本地存档大小
- 调试和校验耗时

以你现在的原生 Web 架构，不做懒加载时，做几百个结构化事件节点通常不会首先撞上浏览器极限；更早出现的问题会是内容一致性、条件组合和测试维护。

## 2. 内容验证上限

真正危险的是组合爆炸。

假设每个事件有多个选择，每个选择又影响：

```text
flag
关系轴
理解等级
地点
物品
时间
后续事件
```

即使事件文件只有几百个，玩家状态组合也可能迅速变得难以测试。

所以“庞大”不能只按 JSON 文件数量衡量，而要看：

```text
状态变量数量
条件组合数量
分支汇合策略
不可逆状态数量
需要回归测试的关键路径数量
```

## 我建议的工程规模

这些是工程规划范围，不是游戏内经济数字，也不是世界观设定：

### 阶段 A：第一条可验证内容链

```text
十几个事件节点以内
一个主要地点
少量核心 NPC
一条小说正史锚点
一条玩家局部介入线
```

目标是验证架构，不是展示规模。

### 阶段 B：第一卷可玩版本

```text
几十到一百多个事件节点
若干地点
一组核心 NPC
若干支线
多个局部汇合点
```

这个规模足以让玩家感到世界有内容，同时还可以依靠完整自动化测试维护。

### 阶段 C：中型完整作品

```text
数百个事件节点
多区域
多条玩家活动线
小说重大事件作为固定锚点
支线在多个位置汇合或结束
```

这是当前架构经过强化后比较合理的长期目标。

### 阶段 D：大型内容工程

```text
上千事件节点
多卷小说
大量 NPC、地区、状态和跨章节依赖
```

不是浏览器一定跑不了，而是必须增加：

- 分卷数据包
- 按章节或区域加载
- 事件图可视化
- flag / topic / NPC 反向索引
- 自动生成引用关系报告
- 分层回归测试
- 存档迁移机制
- 正史一致性检查
- 内容版本和弃用策略

在没有这些工具之前，不建议直接以“大型作品”作为第一阶段目标。

## 我的实际建议

现在不要先决定“我要做上千个节点”。更稳妥的是：

```text
先完成一个 10–20 个节点的完整垂直切片
```

这个切片必须同时包含：

- 小说主角线的一个正史锚点
- 玩家自己的局部线
- 玩家不在场时的世界推进
- 玩家在场时的观察或介入
- 一个不可改变的重大结果
- 一个玩家可以改变的局部结果
- 一个理解等级变化
- 一个事件 flag
- 一个存档和读档回归测试

如果这个切片跑通，才能判断后续扩大到几百个节点是否合适。

# 五、当前最关键的工程判断

现在最危险的不是 `data/events/` 为空，而是**文档已经定义了事件系统，但代码和数据之间还没有形成可执行契约**。

当前应该优先确认这几件事：

1. `data/events/` 的最终目录和文件加载方式
2. Event Node Schema 的最终版本
3. Condition DSL 的最终白名单
4. Effect DSL 的最终白名单
5. 小说正史事件如何表示
6. 玩家线如何观察或介入正史事件
7. 不在场时世界如何推进
8. 错过事件后如何生成可观察后果
9. 哪些状态可以被玩家改变，哪些状态绝对不能改变
10. 事件执行失败时如何回滚
11. 事件图如何检查孤儿节点和死锁
12. 小说 ID、NPC ID、地点 ID 和游戏事件 ID 如何统一

其中第 5–8 项是双作品结构新增的核心，旧的单线事件设计不能直接覆盖。

另外，代码搜索结果本身受返回条数限制，刚才看到的匹配不一定是完整集合；我会把它们当作定位线索，而不是完整审计结果。GitHub 代码搜索入口可以继续查看完整匹配。
